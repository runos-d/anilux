## Первый переход на localhost:5173

Это dev-сервер Vite: первая навигация ждала преобразования цепочки Vue/import, затем использовала кеш. Добавлены `server.warmup` и прогрев кода двух частых направлений после начального содержимого и по намерению перейти. Прогрев не делает API-запросов, учитывает Save-Data и медленное соединение.

Убрана предварительная загрузка неактивных разделов аниме, закрытых редакторов/комментариев ленты, окон карточек и выключенных эффектов курсора. Закрытые окна карточек теперь не создаются для каждого элемента списка. Исправлен обнаруженный тестами дублирующий v-if в FranchiseCard.

Отдельно выявлена задержка loopback-подключения: локальный Docker backend слушает IPv4 (127.0.0.1:8000), а обращение через localhost в этой Windows-среде добавляло около двух секунд. В dev-режиме локальный API теперь использует тот же origin, что и frontend, а Vite проксирует HTTP/media/WS на 127.0.0.1. Host локального сайта сохранён для cookies и абсолютных ссылок; явно настроенный удалённый API и production-конфигурация сохраняются. Заодно папки обсуждений используют общий media URL resolver вместо формирования undefined/media при пустом VITE_API_URL.

Реальные публичные чтения без fixtures после изменения: localhost:8000 — 2227/2076 мс; 127.0.0.1:8000 — 18/46 мс; через localhost:5173/api — 102/20 мс. Это замер отдельных запросов, не полного открытия страницы. Данные: local-api-routing-fixed.json.

Свежий браузер, прогретый Vite, API fixtures, Service Worker выключен: содержимое ленты примерно 1,1 с при первом переходе и 50 мс повторно; рекомендации — 360 мс и 80 мс. Это проверка загрузки клиентского кода, не замер рабочей БД или холодного старта dev-сервера. Результат: `2026-10-28-performance-evidence/browser-fixed-navigation.json`.

## Проверки

Итог: **114 backend-тестов на MySQL и 269 frontend-тестов прошли**. После последней правки API/media-routing дополнительно прошли 15 целевых frontend-тестов. Production build, vue-tsc, eslint и bundle budgets прошли: entry JS 146 955 байта, CSS 70 960 байт.

- Полный migrate на отдельной MySQL 8 прошёл. `makemigrations --check --dry-run`: изменений нет.
- 72 маршрута с fixtures: ошибок JS и горизонтального переполнения на desktop/390px нет.
- Просмотр сохраняет серию 5; уход во время задержанной загрузки не создаёт player и последующие запросы старого экрана.
- Лента виртуализирована: 9 карточек и 1184 DOM-элемента оставались постоянными до 180 загруженных публикаций; JS heap примерно 12–24 МиБ в этой пробе.
- SQL на 10 000 аниме: неизвестный slug 3 запроса и 0 Python slug-преобразований; detail без скриншотов 1 запрос, 0 обращений к провайдеру; 20 франшиз 4 запроса; поиск 20 contact-only аватаров 3 запроса. Каталог после прогрева — 0 SQL. Запрос page_size=500 ограничен 100 карточками.
- Presence 1000 записей: ZRANGEBYSCORE + один MGET, без KEYS и чтения каждого профиля отдельно.
- 100 одновременных WS оставались открытыми после idle-интервала. Все 30 адресных событий получил один адресат, остальные 99 — ни одного; 30 проверок сессии вместо 3000. RSS процесса около 251 МиБ.
- Реальный Celery worker и FFmpeg с локальным тестовым MP4: HTTP 202, затем готовый файл; импорт двух существующих тайтлов тоже 202 → ready. Внешний HTTP в проверочных app/worker запрещён.
- Async file fallback и nginx X-Accel: bytes=2-4 → 206, Content-Range bytes 2-4/10, тело 234. Прямой внутренний путь nginx закрыт 404. Проверка поймала и исправила конфликт `format=mp4/mp3` с DRF renderer negotiation.
- При pause отдельного Redis: readiness 503 за 1603 мс; liveness 200; API 503/Retry-After за 70 и 29 мс. После unpause и cooldown readiness/API вернулись к 200.

## Измеренная нагрузка и ограничения

Это короткие пробы на общей рабочей машине, не длительный production soak-test. Синтетические данные: 10 000 аниме и 101 пользователь, 100 действующих привязанных к сессии access-токенов. Реальный Kodik/CDN и внешняя видеосеть не проверялись.

Один HTTP-процесс с лимитом 2 CPU: 25 авторизованных запросов/с без ошибок, p95 около 151 мс; 50/с также завершились 200, но p95 вырос примерно до 979 мс. При подаче 100/с один процесс перегружался и ограничивал приём кодом 503. Две реплики тоже не дали стабильных 100/с в этой среде; результаты сохранены, они не считаются успешным прохождением этого уровня нагрузки.

Четыре HTTP-реплики через nginx: подача 100 запросов/с 20 секунд, 2000/2000 ответов 200; фактическая скорость с учётом завершения хвоста около 95/с, p95 1524 мс, p99 1935 мс. На каждую реплику выделялось до 2 CPU/1 ГиБ, MySQL — до 2 CPU/1 ГиБ. Для низкого p95 на более высокой нагрузке потребуется подобрать число реплик и ресурсы под рабочие данные и целевой SLO. Универсальная гарантия «любая нагрузка без задержек» этими проверками не подтверждается.

Артефакты: `http-websocket-fixed.json`, `http-scaled-fixed.json`, `http-scaled-four-fixed.json`, `worker-transport-fixed.json`, `redis-fault-fixed.json`, `backend-fixed.json` в каталоге evidence. Файлы токенов в репозиторий не сохраняются.

## Доставка

Локальный запуск обновлён 29 октября: создан SQL-backup 83 784 982 байта в backend/data/backups (путь исключён из Git), восстановлен в отдельной MySQL, миграции проверены на копии с сохранением числа аниме/пользователей/сообщений. Затем полный migrate выполнен в локальном backend; backend, celery_worker и celery_beat перезапущены, download_worker и catalog_import_worker собраны и запущены. Readiness сообщает database/cache/channels=ok; регистрация новых tasks и потребление обеих выделенных очередей проверены. Многорепличная конфигурация не включалась в пользовательском окружении.

Для переноса этих изменений в другой запуск:

1. Следовать принятой процедуре резервного копирования БД/медиа и пересобрать образы backend/frontend с этим исходным кодом.
2. Выполнить полный `migrate` через сервис migrate. Включает anime.0017, seo.0006, users.0015 и ещё не доставленную users.0014 предыдущего исправления.
3. Обновить backend, celery_worker, celery_beat, download_worker, catalog_import_worker и frontend/nginx. Все реплики и download_worker должны видеть одну директорию `backend/data/private_downloads`; nginx монтирует её только для чтения вне публичного MEDIA.
4. Проверить `/health/ready/`, регистрацию новых Celery tasks и две выделенные очереди. Без workers новые операции останутся в ожидании до истечения срока задания.
5. Для нескольких HTTP-реплик добавить `-f docker-compose.scaled.yml` после основного и production-файлов. По умолчанию 4 реплики; число меняется BACKEND_REPLICAS. В этом варианте прямой backend port убран, API идёт через nginx. Это отдельная конфигурация для production, не замена Vite на localhost:5173.

Compose конфигурации проверены командой `config --quiet`; nginx прошёл `nginx -t`. Проверочные контейнеры/тома/сеть и браузер удалены после проверки. Локальные рабочие сервисы и резервная копия сохраняются.
