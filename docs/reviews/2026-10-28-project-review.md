## Срочные дефекты

### R01 · P0 · Гость может изменять и удалять аниме

**Код:** `backend/apps/anime/presentation/views/anime_views.py:102–105`; `backend/apps/anime/presentation/serializers/anime_serializers.py:119–142`; регистрация router в `backend/apps/anime/presentation/urls.py`.

`AnimeViewSet` наследует полный `ModelViewSet`, имеет `AllowAny` и не ограничивает стандартные create/update/destroy. Большинство полей сериализатора доступны для записи. На изолированной записи гостевой `PATCH /api/anime/audit-anime/` изменил описание и вернул **200**, последующий `DELETE` вернул **204**. Удаление аниме также затрагивает связанные записи через каскады.

**Исправление:** публичный каталог сделать ReadOnlyModelViewSet; изменения вынести в явно административный API либо задать отдельные права для небезопасных методов. Обязательные проверки запрета POST/PATCH/PUT/DELETE гостю и обычному пользователю.

### R02 · P1 · Realtime HTTP API раскрывает события других получателей

**Код:** `backend/apps/users/presentation/views/users_views.py:793–799`; `backend/core/redis_events.py:27–65`.

`GET /api/users/realtime/` возвращает общую Redis-очередь без проверки `target_users`, членства в чате или видимости объекта. WebSocket фильтрует получателей, но этот HTTP-вход обходит фильтрацию. Диагностический вызов от пользователя A вернул событие с текстом сообщения и `target_users=[B]`. Очередь может содержать события старых realtime publishers и consumers; существование этого входа не зависит от того, какой клиентский транспорт используется сейчас.

**Исправление:** удалить ненужный endpoint либо выполнять ту же проверку получателя и доступа, что в WebSocket/event projection; ограничить и валидировать limit.

### R03 · P1 · Настройки скрытия контактов и фото не обеспечиваются сервером

**Код:** `backend/apps/users/presentation/views/users_views.py:685–760`; `backend/apps/users/presentation/serializers/users_serializers.py:64–133,230–252`.

Поиск использует полный `UserSerializer`, который отдаёт email, телефон и last_login любому вошедшему пользователю. При `who_can_see_email=nobody` и `who_can_see_phone=nobody` другой пользователь получил **200** с обоими скрытыми контактами. Публичный профиль гостю также вернул `avatar_url` при `who_can_see_profile_photo=nobody`. Аналогичные пути с UserSimpleSerializer и выдачей картинок не применяют политику. Наличие отдельного `check_visibility` не защищает данные, уже попавшие в ответ; nginx и media URL также отдают файл независимо от настройки.

**Исправление:** единая серверная проекция пользователя с учётом просматривающего и приватности во всех ответах; отдельно определить правила доступа/кеширования фото. Проверять чтение закрытых полей, а не только сохранение переключателя.

### R04 · P1 · Можно самостоятельно подтвердить email и телефон; смена email сохраняет подтверждение

**Код:** `backend/apps/users/presentation/views/users_views.py:521–529`; `backend/apps/users/presentation/serializers/users_serializers.py:64–149`.

В `UserSerializer.read_only_fields` отсутствуют `email_verified`, `phone_verified`, `two_factor_enabled`. PATCH собственного `/api/users/profile/` с двумя флагами true вернул **200** и сохранил оба. Отдельный тест заменил email уже подтверждённого пользователя: новый адрес остался `email_verified=True` без подтверждения владения.

**Исправление:** сделать служебные флаги недоступными для записи профиля; изменение email оформлять отдельным подтверждаемым процессом со сбросом старого статуса. Проверить все входы обновления пользователя, включая `/me/` и settings/all.

### R05 · P1 · «Завершить сессии» не отзывает JWT

**Код:** `backend/apps/users/presentation/views/users_views.py:633–650,937–992`; выдача JWT в LoginView.

Terminate удаляет Django Session/ActiveSession, тогда как приложение продолжает авторизоваться через access/refresh JWT. После успешного **200** от `/api/users/sessions/terminate-all/` ранее выданный refresh успешно получил новый access (**200**). Закрытие сессии не прекращает доступ другого устройства.

**Исправление:** связать сессии с refresh-токенами/семействами токенов и отзывать соответствующие credentials. Определить политику текущих access-токенов и WebSocket. Проверять запрет refresh после завершения сессии.

### R06 · P1 · Удаление аккаунта ломает пересланные файлы другого пользователя

**Код:** `backend/apps/users/application/data_management.py:278–319`; `backend/apps/social/presentation/views/conversation_views.py:349–355`.

Пересылка создаёт Attachment с тем же именем физического файла. `_collect_user_files` собирает FileField удаляемых объектов, а `delete_user_account` без проверки оставшихся ссылок вызывает `storage.delete(name)`. В тесте после удаления автора исходного сообщения Attachment пересланного сообщения в другом чате сохранился, но его файл уже отсутствовал (**record=True, file=False**).

**Исправление:** согласовать удаление с общей системой ссылок/GC; удалять файл только после проверки всех оставшихся владельцев ссылок либо создавать независимую копию при пересылке. Проверять пересланные media/thumbnail, а не только основной файл.

### R07 · P1 · Запрет пересылки сообщений не действует

**Код:** `backend/apps/social/presentation/views/conversation_views.py:330–359`; `PrivacySettings.allow_message_forwarding`.

Обработчик учитывает групповое `restrict_saving_content`, но не пользовательский `allow_message_forwarding`. При выключенной пересылке у автора получатель смог переслать его личное сообщение в третий чат: **201**.

**Исправление:** проверять политику автора исходного сообщения в общей команде пересылки. Применять её ко всем транспортам и пересылкам файлов/карточек.

### R08 · P1 · Неопубликованные новости доступны по прямому ID

**Код:** `backend/apps/social/presentation/views/views_news.py:24–38`.

Список фильтрует `is_published`, а NewsDetailView с `AllowAny` читает все новости. Гостевой GET неопубликованной новости вернул **200**. Порядковый ID позволяет перебрать черновики.

**Исправление:** использовать одинаковую проекцию видимости в list/detail; черновики возвращать только авторизованной редакции.

## Функциональность и производительность

### R09 · P2 · Поиск удаляет букву s

**Код:** `frontend/src/composables/useSearch.ts:6–10`.

В character class регулярного выражения записано `\\s`: это удаляет обратную косую черту и букву `s`, а не обозначает только пробельные символы. В Chromium ввод `sword` отправил **`/api/anime/?search=word&page_size=5`**. Английские названия с этой буквой искажаются.

**Исправление:** поправить class и добавить проверки английских названий, пробелов и пунктуации.

### R10 · P2 · Старый ответ поиска подменяет новый

**Код:** `frontend/src/composables/useSearch.ts:159–239,242–269`.

Debounce отменяет только ожидающий таймер. Уже отправленный performSearch не отменяется и не проверяет поколение/текущий запрос; завершившись, безусловно пишет results. Медленный ответ A после более быстрого B показывает результаты A при строке B. После очистки строки поздний ответ снова заполняет подсказки. Таймер не снимается при уничтожении composable.

**Исправление:** AbortController и/или счётчик поколения, сброс loading только для актуального поиска, dispose таймера.

### R11 · P2 · Выбор плейлиста в поиске ведёт на несуществующий маршрут

**Код:** `frontend/src/composables/useSearch.ts:286–296`; `frontend/src/router/index.ts:371`.

Выбор вызывает `/playlists/{id}`, но detail зарегистрирован как **`/playlist/{id}`**. В мобильном меню SearchBar используется с категориями по умолчанию, включающими playlists, поэтому путь достижим. На десктопе navbar сейчас ищет только anime.

**Исправление:** переходить по имени маршрута `playlist-detail`.

### R12 · P2 · Главная делает N дополнительных запросов полных карточек

**Код:** `frontend/src/components/page/other/HomeHero.vue:175–187,422–424`.

После общего home-запроса компонент сразу запрашивает детали каждого элемента через Promise.all, включая невидимые слайды. В гостевом открытии зафиксировано **24 дополнительных GET `/api/anime/{id}/`**. Эти детальные ответы могут дополнительно вызывать внешнее получение скриншотов на backend (`AnimeViewSet.retrieve:490–501`).

**Исправление:** возвращать нужное описание/постер в home-проекции; либо загружать текущий слайд и максимум следующий, с кешем и лимитом параллелизма.

### R13 · P2 · Гость постоянно запрашивает избранное и получает 401

**Код:** `frontend/src/composables/useFavorite.ts:9–12,38`; `frontend/src/stores/favorites.ts:103–118`.

Каждый экземпляр useFavorite вызывает ensureLoaded без проверки авторизации. После ошибки store остаётся незагруженным, а очередная карточка/смена hero повторяет запрос. За одну гостевую сессию зафиксировано **7 ответов 401** на `/api/playlists/favorites/anime/ids/` до подмены API fixtures.

**Исправление:** не загружать приватный список гостю; запускать загрузку при подтверждённом входе и учитывать повтор после ошибки отдельно от каждого mount.

### R14 · P2 · «Смотреть» в hero начинает с последней серии

**Код:** `frontend/src/components/page/other/HomeHero.vue:154–158,297–321`.

`resolveEpisodes` возвращает общее количество серий, но goToWatch использует его как номер стартовой серии. Для тайтла из 12 серий кнопка формирует `?episode=12`; AnimeWatchView при явном query.episode предпочитает его сохранённому прогрессу. Возможны спойлеры и ошибочный старт.

**Исправление:** для нового просмотра первая серия, для продолжения — явная сохранённая цель из серверных данных; total episodes не является resume target.

### R15 · P2 · Плеер проверяет наличие в библиотеке только по первой странице

**Код:** `frontend/src/components/page/anime/AnimeWatchView.vue:1412–1456`; `backend/apps/users/application/views_library.py:13–16,490–543,644–659`.

checkLibraryStatus загружает `/users/library/` без фильтра и ищет аниме только в results. API возвращает **24** элемента. Тайтл на второй странице считается отсутствующим, теряются libraryItemId и позиция; попытка авто-добавления получает конфликт и повторяет такую же неполную проверку. Уже существует точечный `/users/library/check_anime/?anime_id=...`. В CollectionButton есть похожая дополнительная загрузка страницы после точечной проверки.

**Исправление:** получать запись конкретного аниме, включая её ID и прогресс; не искать существование в страничном списке.

### R16 · P2 · При переходах между тайтлами остаются старые activity timers

**Код:** `frontend/src/components/page/anime/AnimeWatchView.vue:1368–1371,2456–2475`; `frontend/src/composables/useAnimeTab.ts:77–97`.

useAnimeTab создаётся после await, вне setup lifecycle: ветка без current instance уже запускает ping/интервал; вызывающий код тут же делает `tab.start()` — второй начальный ping. При изменении slug новый tab заменяет animeTab без stop старого. При окончательном unmount останавливается только последний экземпляр. Старые интервалы продолжают писать active-tab для прежних аниме и слушать visibilitychange.

**Исправление:** один явный start; stop перед заменой тайтла и при dispose; проверить сетевой журнал после A→B→C и ухода из плеера.

### R17 · P2 · Прогресс просмотра не изолирован между аккаунтами

**Код:** `frontend/src/stores/watchProgress.ts:34–50`; `frontend/src/components/page/anime/AnimeWatchView.vue:2342–2373`; `frontend/src/main.ts:49–62`.

progressMap индексируется только animeId и не очищается при logout/смене пользователя. `anime_progress_{animeId}` в localStorage тоже не содержит владельца. loadWatchProgress предпочитает эти данные. После A→logout→B на одном устройстве старые позиции могут попасть в отображение и последующее сохранение B.

**Исправление:** scope данных по accountId, полный reset runtime при смене аккаунта, отдельная явно выбранная политика гостевого прогресса.

### R18 · P2 · Согласие предыдущего аккаунта перезаписывает решение следующего

**Код:** `frontend/src/analytics/consent.ts:3–31`; `frontend/src/analytics/consentSync.ts:14–30`; `frontend/src/main.ts:49–61`.

Согласие хранится глобально на браузер. При смене пользователя syncConsent читает локальное решение и всегда PATCH-ит его на новый аккаунт, даже если сервер этого аккаунта вернул другое решение. Например, локальное granted от A заменит сохранённое denied у B. Время решений не сравнивается, принадлежность не учитывается. Даже одинаковое решение создаёт лишнюю запись и обновляет consent_updated_at при загрузке профиля.

**Исправление:** явно определить политику согласия устройства и аккаунта; не выдавать старую запись устройства за новое решение другого пользователя; сравнивать версию/принадлежность/время и не PATCH-ить равные значения.

### R19 · P2 · Выбор в баннере не сохраняется на сервере текущего аккаунта

**Код:** `frontend/src/components/privacy/AnalyticsConsentBanner.vue:27–28`; `frontend/src/main.ts:49–61`.

Кнопки вызывают только setConsent. syncConsent запускается при изменении user.id, а не при выборе в баннере. Если пользователь уже вошёл и id не меняется, сервер остаётся в прежнем состоянии до перезагрузки/следующего изменения аккаунта. Отдельная форма PrivacySettings делает PATCH, поэтому два интерфейса работают по-разному.

**Исправление:** единый контроллер изменения согласия с локальным применением и адресной серверной синхронизацией подтверждённого аккаунта.

### R20 · P2 · Отзыв согласия не применяется в других открытых вкладках

**Исправление:** синхронизировать решения между вкладками и применять consentChanged/reset во всех активных экземплярах.

### R25 · P2 · Кеш legacy screens всегда повторно запрашивает свежие данные

**Код:** `frontend/src/composables/useCachedReads.ts:29,36–42`; `frontend/src/lib/queryClient.ts:5–8`.

Наличие cached data всё равно вызывает refresh с `staleTime:0`. Настроенные глобально 60 секунд свежести не учитываются. Повторное открытие раздела или тот же read создаёт GET даже для только что загруженного результата. Кеш даёт быстрый показ, но не сокращает эти запросы.

**Исправление:** проверять dataUpdatedAt/isInvalidated и актуальное staleTime; принудительный refresh оставить для invalidation и явного обновления. Сохранить обновление скрытого экрана при возврате после invalidation.

### R26 · P2 · Автосохранения приватности могут записать устаревший набор настроек

**Код:** `frontend/src/components/settings/PrivacySettings.vue:326–340`.

Каждое переключение сразу отправляет полный privacySettings без очереди или блокировки. Два быстрых изменения создают параллельные PATCH со снимками A и B; при обратном порядке обработки сервер заканчивает на A. Успешный ответ при этом копирует в originalSettings текущее состояние формы, а не реально отправленный/возвращённый снимок, и показывает «сохранено».

**Исправление:** последовательное сохранение последнего снимка или PATCH только изменённого поля с контролем порядка; обновлять originalSettings из принятого ответа.
