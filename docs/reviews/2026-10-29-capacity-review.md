# Подготовка к 6000 активных пользователей — 29 октября 2026

**Статус: цель 6000 активных пользователей не подтверждена.** Внесены и проверены оптимизации, подготовлены конфигурации нескольких хостов. На локальном смешанном тесте при повышении активности остаётся очередь доставки чата. Это незакрытый критерий производительности, его нельзя подменять количеством открытых WebSocket или зелёными функциональными тестами.

Вводные владельца: 4 vCPU, 8 GiB RAM, 80 GB NVMe, 1 Gbit/s; много действий и чата, можно добавить сервер. Уточнение: несколько комнат на тысячи участников и комнаты на сотни; приоритет — общие оптимизации без чрезмерного усложнения. Ранее названные 10 000 ₽/месяц больше не являются ограничением работы над кодом. Удалённые серверы не покупались, не переносились и не настраивались. Предварительный план размещения: [deploy/README.md](../../deploy/README.md).

## Исправления этого прохода

| Проблема | Изменение и границы |
|---|---|
| После остановки/падения API оставались Redis группы несуществующих сокетов на срок до суток | Default group expiry сокращён до 300 с; активные consumer subscriptions продлеваются аутентифицированным heartbeat в той же очереди, что subscribe/unsubscribe. Pipeline ограничен 256 groups, renewal error вызывает reconnect. При rolling upgrade нужен двухэтапный переход TTL, описанный в deploy/README. Рабочий Redis не очищается. |
| Fanout делал Redis roundtrips даже для пустых адресных групп | Актуальные `ZCOUNT` проверяются pipeline по 256 имён; пустые/истёкшие группы пропускаются, остальные используют штатный `group_send`. Ошибки не маскируются, outbox остаётся retryable. |
| PyMySQL 1.2.3 загружал системные CA при каждом новом DB connection | Тонкий Django backend переиспользует только неизменяемый default SSLContext. TLS negotiation/verification policy сохранена, явные CA/cert/options не кешируются, после fork context/lock сбрасываются. DB connections и auth decisions не кешируются; `CONN_MAX_AGE=0` сохранён. Есть opt-out `DB_TLS_CONTEXT_CACHE=false`. |
| История и команды независимых WS-комнат стояли в одном DB executor | Authorize/snapshot/commands и отдельные global readers используют bounded default thread pool через `database_sync_to_async(thread_sensitive=False)`. Каждая операция владеет своим thread-local DB connection с cleanup до/после; ORM connections между потоками не передаются. DB locks/idempotency внутри одной беседы остаются. Штатный Channels dispatch сохранён. |
| Периодический HTTP heartbeat и pending-post polling при уже открытом WS | Presence/visibility передаются в global WS; HTTP остаётся fallback с jitter. При отсутствии processing jobs post polling приостанавливается; остаются редкая сверка и восстановление после reconnect. Появление новой processing job сразу переводит idle polling обратно на интервал 3 с; logout отменяет оба watcher и таймеры. |
| Повторный HTTP GET карточки чата на каждое новое сообщение | Viewer-specific WS событие содержит unread count. Клиент обновляет preview/read/unread из DTO с защитой от старых sequence/version; структурные изменения и старый backend используют HTTP fallback. Удаление старого unread сообщения также обновляет счётчик. |
| Публичные post events заставляли клиентов повторно грузить ленту/карточки | Известные счётчики патчатся из события, неизвестные посты не запрашиваются каждым зрителем. Новые посты показывают существующий баннер обновления, лента перечитывается по действию пользователя. |
| Отдельные SQL-проверки каждой текущей WS-сессии | Concurrent проверки объединены в ограниченные batches. Активность аккаунта, живой server session, password hash, token version и expiry перечитываются; результатов предыдущих batches нет в auth cache. |
| SQL и сериализация сообщения отдельно для каждого получателя | Для обычных сообщений без цитат/вложений текущие ACL, bounds истории, receipts и unread вычисляются пакетно. Общие поля форматируются без viewer, персональные поля добавляются после текущей проверки. Повторно используются только viewer-free метаданные полей сериализатора. Сложные сообщения сохраняют общий персональный reader. |
| Стандартное чтение ACL отдельно для каждого слушателя комнаты | Текущие active users, public/private membership и bans проверяются одним bounded batch. После DB failure чтение не разрешается. |
| DB connections из presence thread pool не закрывались тем потоком, который их открывал | Presence использует `database_sync_to_async` с cleanup до/после операции. Штатный Channels dispatch сохранён. |
| Новый сериализатор для каждого сообщения истории | История использует один `MessageSerializer(..., many=True)` с общим viewer context. |
| Лишние event loops/Redis операции на fanout | Доставка outbox использует один loop и до 16 одновременных group sends. Адресные пакеты содержат одного получателя вместо полного списка группы в каждом пакете. |
| Синхронные reconnect bursts, большие/частые входящие frames, неограниченный handshake burst | Reconnect jitter; frame budget 64 KiB, 10/s с burst 30; отдельный лимит pending handshakes. Некорректный JSON закрывается с protocol error. Эти пределы защищают процесс, но не доказывают capacity. |
| `COALESCE(published_at,created_at)` мешал индексному чтению ленты | Миграция social.0038 добавляет stored generated `feed_sort_at` и покрывающий индекс. Сохраняется порядок публикации и keyset cursor; обычная прокрутка запрашивает `include_count=false`, legacy точный count остаётся по умолчанию. |
| WS query token попадал в nginx error URL | Новый frontend передаёт credential через subprotocol header; сервер выбирает только `animecore.v2`. В новых role env query tokens выключены. Legacy разрешён по умолчанию для совместимости; после обновления frontend его следует отключить. Access logs исключают query; credential headers не логируются. |
| Redis password учитывался не всеми клиентами | Channel/cache/Celery URL используют одинаковое экранирование пароля; поддержан private IPv6. Проверены URL parsers Redis и Kombu. |
| Все сервисы и native builds конкурировали бы за небольшой VPS | Подготовлены app/data/workers/TLS edge compose роли с CPU/RAM/FD/log bounds, singleton beat и отдельными очередями. В app-роли отключён auto native build. Это конфигурации для дальнейшего развёртывания, не выполненный remote deployment. |

## Измерения

Отдельная Docker-сеть и MySQL schema `audit-mysql/chat_test`, реальные миграции, Redis и Celery; read-only mounts исходников. Начальный fixture: 6000 bound sessions, 100 комнат по 60 участников, 10 сообщений истории на комнату, 10 000 anime, 60 000 постов. Последний короткий прогон: 120 аккаунтов/две комнаты, те же 60 000 постов. Рабочие пользователи/переписка не использовались для нагрузки.

- **TLS A/B, 20 новых DB connections + SELECT 1/close:** CPU 938,3 → 262,6 мс, примерно на 72% меньше в операции подключения. Default TLS и required/verification flags совпали. Это не ускорение сайта в целом на 72%. [Данные](2026-10-29-capacity-evidence/tls-connection-comparison.json), [воспроизводимый probe](2026-10-29-capacity-evidence/tls_connection_benchmark.py).
- **После TLS fix, до переноса одиночных readers в pool:** на 120 пользователях все 200 HTTP, 20 ACK и 2400 доставок получены, p95 HTTP 297 мс, доставки 1,10 с. Порог доставки <1 с не пройден. Расширение auth-batch window до 20 мс улучшения не дало и было удалено. [Данные](2026-10-29-capacity-evidence/mixed-120-tls-cache.json).
- **Три комнаты по 2000 участников, ramp до pool change:** при batch 32 остановка после 3616 попыток пользователей, 7124 открытых WS, 108 failures/closures. p95 snapshot 3,06 с. Смешанная стадия не начиналась, цель 6000 не достигнута. [Данные](2026-10-29-capacity-evidence/ramp-large-rooms-before-parallel-db.json).
- **Следующий ramp, до последующего group-expiry fix:** batch 16, остановка после 4976 попыток, 9852 открытых WS, 100 ответов 502, p95 snapshot 3,91 с. Batch отличается от предыдущего; эти цифры не доказывают коэффициент ускорения pool change. В nginx есть connection reset/no live upstreams. Это не успешный тест 6000. [Данные](2026-10-29-capacity-evidence/ramp-large-rooms-parallel-db.json).
- **Пустые Redis groups, A/B:** 2000 адресатов, 120 с активным каналом, уникальный prefix, проверка всех 120 получателей в каждом из трёх повторов. Исходный fanout 619–1121 мс, pipeline-предварительный отбор 93–121 мс. [Данные](2026-10-29-capacity-evidence/group-fanout-comparison.json). Это не полная доставка через БД/Celery.
- **Диагностика реального worker:** несмотря на быстрый isolated fanout, оставшиеся от прошлых процессов group entries вызывали обработку несуществующих сокетов. В этой фазе task занимала 1,38–1,70 с, из них user groups 1,27–1,58 с; outbox age при 1 send/с вырастал в среднем примерно до 10 с. [Worker timing](2026-10-29-capacity-evidence/worker-fanout-timing.jsonl).
- **После group expiry/renewal, итоговый сохраняемый вариант:** 120 активных из 2000 членов комнаты, 10 HTTP/с + 1 send/с, 20 с — 200/200 HTTP, 20/20 ACK, 4800/4800 уникальных доставок; p95 HTTP 333 мс, доставки 969 мс. Следующая ступень 30 HTTP/с + 2 sends/с не прошла (p95 доставки полученных в окно кадров 20,74 с). [Данные](2026-10-29-capacity-evidence/mixed-120-in-large-room-group-expiry.json). Первоначально до очистки истёкших memberships первая ступень имела p95 10,65 с и только 3600/4800 доставок в окно; исторические результаты сохранены отдельно.

- **Лента, 60 000 постов:** до индекса/отказа от ненужного count одиночные запросы занимали примерно 327–375 мс. После индекса с точным count — 132–179 мс; обычная страница без count — около 37–40 мс, weighted без count — около 40–66 мс. Это одиночные локальные чтения, не end-to-end открытие страницы и не 1200 RPS. [Данные](2026-10-29-capacity-evidence/feed-index-profile.json).
- **Проекция одного обычного сообщения для 60 пользователей:** исходный персональный reader — 1021 SQL / около 1716 мс; bulk reader — 7 SQL / около 34 мс, DTO совпали. Замер не включает общую очередь Celery/WS и поэтому не равен времени доставки. [Данные](2026-10-29-capacity-evidence/projection-profile.json).
- **История из 10 сообщений, 40 повторов:** отдельные сериализаторы — около 1885 мс, общий — около 406 мс; ответы совпали. Ускорение примерно 4,6× относится к этой операции.
- **Попытка разгона к 6000 до последних оптимизаций:** остановка после 4544 попыток пользователей, 8880 открытых sockets, 208 неудачных соединений; p95 snapshot около 4,76 с. Цель не достигнута. Это не предел финальной production версии. [Данные](2026-10-29-capacity-evidence/ramp-6000.json).
- **Финальная короткая ступень, 120 пользователей/240 WS, 20 с:** 10 HTTP/с и 1 сообщение/с в комнате из 60 участников — HTTP 200/200, ACK 20/20, 2400/2400 уникальных доставок, посторонних получателей 0. p95 HTTP около 291 мс, ACK 429 мс, доставки 808 мс. Она прошла заданный порог p95 <1 с.
- **Следующая ступень тех же пользователей:** 30 HTTP/с и 2 сообщения/с, 20 с — HTTP 600/600, ACK 40/40, но в окно измерения пришли 3015 из 4800 ожидаемых уникальных доставок; p95 доставленных кадров около 14,3 с. Ступень **не прошла**. Данные сохраняются в outbox, это не доказательство утраты сообщений, но задержка неприемлема. [Обе ступени](2026-10-29-capacity-evidence/mixed-120-final.json).

Ресурсы теста: четыре API по 1 CPU/1 GiB, MySQL 2 CPU/2 GiB, Redis 512 MiB, events worker 1 CPU/768 MiB, gateway 0,5 CPU/256 MiB. Docker Desktop использует общий хост 8 CPU/~15,5 GiB, на нём работают и другие сервисы. Это больше CPU, чем один VPS 4 CPU для всех ролей; результаты не экстраполируются в гарантированный production онлайн. Генератор учитывает ошибки, p95, ACK и уникальных получателей, проверяет изоляцию всех реплик и не прячет отказы retries.

Эксперимент с объединением auth/ACL/projection callback сократил число SQL, но на полном mix не улучшил задержки и был удалён из итоговой реализации. Профиль и результат сохранены как диагностические, не как производительность итогового кода: `mixed-120-combined-reader-experiment.json`.

## Проверки и локальная поставка

Финальный список проверок и counts записан в [validation.json](2026-10-29-capacity-evidence/validation.json). Проверены MySQL regression tests, privacy/revocation, payload equivalence для разных viewers, read/clear/join/bans, rich-message fallback, subprotocol auth, frame/admission bounds, frontend tests, types/lint/build/bundle budget, compose config и nginx syntax. Итоговый backend прошёл 246 regression tests на MySQL/Redis за 292,775 с, включая отзыв авторизации после успешной доставки, expiry обоих типов событий, group renewal и независимость комнат. Schema/model drift не найден. Полный длительный production soak/6000 mixed test не выполнен.

Миграция social.0038 прошла на тестовой базе с 60 000 постов, `makemigrations --check --dry-run` не нашёл drift. Перед локальной миграцией сохранён новый ignored SQL backup 84 830 859 bytes в `backend/data/backups/before-capacity-fixes-20261029-104424.sql`; предыдущие backups сохранены. Затем применена миграция, обновлены локальные backend/worker/beat и выделенные media/import workers. Проверки локальной схемы/миграций успешны, readiness 200 напрямую и через Vite, анонимный каталог через localhost:5173 — 200. [HTTP smoke](2026-10-29-capacity-evidence/local-readiness.json).

После дополнительного прохода обновлены локальные backend, worker/beat и выделенные media/import workers; перед restart выполняющихся application jobs не было. Проверены `CachedTLSConnection`, фактический `SSLSocket`, `CONN_MAX_AGE=0` и group expiry 300 с. Readiness и каталог через localhost:5173 возвращают 200; новые миграции не требуются.

Изолированные test containers, network и volume удалены; рабочие anilux сервисы и backups сохранены. Автоматическая проверка запретила как пакетное, так и точечное удаление созданных временных файлов с причиной `blocked by policy`: в Temp остались `animecore-capacity-fixture.log`, `animecore-capacity-final-fixture.log` с синтетическими credentials и `animecore-capacity-config-validation/` с dummy TLS certificate/key. К ним добавились временные fixture logs повторного прохода (`phase2`, `large-room`, `fanout`, `combined`) с такими же синтетическими credentials и schema-only SQL в Windows Temp. Они не содержат production credentials; использовать их для рабочего deployment нельзя. Обход запрета не выполнялся. Ничего не committed/pushed и не развёрнуто на удалённых платных серверах.

## Что остаётся до запуска 6000

1. Довести end-to-end chat fanout до согласованного p95 при одновременных HTTP/actions. Низкое число SQL в одной bulk операции не доказывает пропускную способность полного transport pipeline; последний смешанный тест всё ещё показывает backlog. Сложные сообщения и длинная unread история требуют отдельных сценариев и дальнейшей оптимизации.
2. Проверить целевые хосты: CPU гарантии, private сеть, диск/backup и трафик. Два хоста — предварительная отправная точка, без HA. Оптимизации кода не подменяются покупкой оборудования; конфигурация RAM/vCPU сама по себе также не доказывает 6000 активных.
3. Прогонять диапазон активности: HTTP/send/read/typing, комнаты на сотни и тысячи участников, пик и длительность. Размеры комнат владелец уже уточнил. Один HTTP каждые 5 с у 6000 пользователей — 1200 HTTP/с, одно сообщение в минуту — 100 sends/с. Эти значения ещё не пройдены. Общая большая комната создаёт больше доставок на сообщение.
4. Согласовать хранение и медиа: при 100 сообщениях/с — 8,64 млн сообщений/сутки; 80 GB не являются долгосрочным запасом. Собственное видео должно обходить app/DB сервер через подходящее media storage/CDN. Не включать автоматическое удаление переписки без решения владельца.
5. На целевой инфраструктуре выполнить 30–60 минут mixed нагрузки, затем soak, reconnect storm, replay и отказ replica/Redis/DB. До успешной приёмки цель 6000 остаётся открытой.
