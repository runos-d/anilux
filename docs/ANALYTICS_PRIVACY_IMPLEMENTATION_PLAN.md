# План реализации аналитики, приватности и управления данными AniLux

Дата аудита: 27 октября 2026 года.

## Цель

Создать проверяемый контур продуктовой аналитики и обезличенной технической телеметрии, который не загружает внешние счётчики до явного согласия, не передаёт пользовательский контент и персональные данные, корректно работает в SPA и не влияет на работу AniLux при отключении провайдеров.

До подключения внешней аналитики необходимо исправить существующие ошибки настроек приватности, экспорта и удаления данных. Простое добавление скрипта Яндекс Метрики или Google Analytics недопустимо.

Связанные GitHub issues: #2, #5-#14.

## Текущее состояние

Положительная сторона: Яндекс Метрика, Google Analytics и внешняя telemetry сейчас не загружаются, поэтому скрытого сбора данных до согласия в текущей версии нет.

### P0 - текущие функциональные и privacy-дефекты

1. Frontend вызывает `GET/PUT /users/privacy-settings/`, но DRF `ModelViewSet` использует collection endpoint для списка и detail endpoint для обновления. Ещё одна реализация обращается к отсутствующему `/users/privacy`. Настройки загружаются некорректно, а обновление может отвечать `404` или `405`.
2. Переключатели геолокации, поиска по телефону, таргетированной рекламы и дополнительных параметров пересылки существуют только в локальном состоянии `PrivacySettings.vue`. Интерфейс может показать успешное сохранение, хотя эти параметры не записаны и ни на что не влияют.
3. `/api/users/analytics/` сериализует `weekly_report`, который обращается к отсутствующим полям `UserSession.start_time` и `UserSession.end_time`. Endpoint падает с `FieldError`. Счётчики `UserAnalytics` нигде не обновляются, а часть отчёта возвращает заглушки.
4. `ExportDataView` возвращает только фиктивное сообщение об успешном запуске. Список экспортов, создание архива, download endpoint и отправка ссылки отсутствуют, хотя frontend сообщает пользователю обратное.
5. Неиспользуемый прототип `StorageService.export_data()` нельзя подключать без переработки: он выбирает сообщения других участников общих чатов и email/телефон контактов без применения их privacy settings.
6. Удаление аккаунта имеет два несовместимых сценария. `DELETE /users/me/` вызывает ручную очистку, а `/users/account-deletion/` сразу вызывает `user.delete()`. Frontend передаёт параметры отложенного удаления, причины, итоговое подтверждение и 2FA, но backend использует только пароль. Endpoint отмены отсутствует.

### P1 - архитектурные недостатки

1. Нет единого analytics API, no-op реализации, consent state, каталога событий, sanitizer, адаптеров провайдеров и безопасного router tracking.
2. Нет разделения между персональной статистикой внутри продукта, агрегированной продуктовой аналитикой и error/performance telemetry. Существующая модель `UserAnalytics` имеет вводящее в заблуждение имя.
3. Ошибки и ответы API местами логируются напрямую, включая Axios error objects, `error.response.data` и URL плеера. Подключение внешнего error tracking поверх текущих console breadcrumbs может передать пользовательские данные и токены.
4. Access и refresh tokens хранятся в `localStorage`. Локальные данные распределены по множеству несогласованных ключей, для них нет единого реестра и lifecycle policy.
5. Нет версионирования согласия, времени принятия решения, правил отзыва и удаления cookies внешних провайдеров.
6. Политика приватности прямо указывает на отсутствие подтверждённых реквизитов оператора, места размещения инфраструктуры и конкретных сроков хранения данных.
7. CSP не подготовлен к безопасному подключению внешних счётчиков: разрешения должны добавляться точечно для script/connect/img endpoints выбранного провайдера, а не общим wildcard.

## Принципы реализации

- Analytics выключена по умолчанию и полностью заменяется no-op реализацией.
- События, возникшие до согласия, отбрасываются и не отправляются задним числом после согласия.
- Неизвестные события и поля отклоняются в development/test.
- Внешним провайдерам доступны только поля из явного allowlist.
- Email, телефон, nickname, токены, содержимое форм, поисковые строки, сообщения, комментарии, названия файлов, query string и fragment запрещены.
- Хеширование прямого пользовательского идентификатора не считается анонимизацией.
- Отказ от аналитики не ухудшает работу приложения.
- Ошибка или отсутствие внешнего SDK не влияет на AniLux.
- Не использовать User-ID, session replay, Webvisor и рекламную персонализацию без отдельного решения.
- Серверные продуктовые данные не дублируются в произвольном event storage без необходимости.

## Этап 0. Исправить существующий контур приватности

1. Сделать единый API текущего пользователя, например:
   - `GET /api/users/privacy-settings/me/`;
   - `PATCH /api/users/privacy-settings/me/`.
2. Удалить обращение к отсутствующему `/users/privacy` и согласовать frontend types с реальной backend schema.
3. Для каждого видимого privacy-переключателя реализовать хранение и применение либо временно удалить недействующий контрол из интерфейса.
4. Добавить contract-тесты чтения, частичного обновления, изоляции пользователей и применения каждого параметра.
5. Не использовать текущую `UserAnalytics` для внешней аналитики. Переименовать её в `UserActivitySummary` и исправить, если персональная статистика действительно нужна, либо удалить модель и endpoint как мёртвую функцию.

## Этап 1. Единый analytics API, sanitizer и каталог событий

Связанные issues: #5, #9, #10.

Предлагаемая структура frontend:

```text
src/analytics/
  core.ts
  types.ts
  catalog.ts
  sanitizer.ts
  consent.ts
  router.ts
  telemetry.ts
  adapters/
    noop.ts
    yandex.ts
    google.ts
```

Публичный API:

- `initialize()`;
- `pageView()`;
- `event()`;
- `consentChanged()`;
- `reset()`.

`identify()` в первой версии не используется. User-ID и устойчивые внешние идентификаторы требуют отдельного privacy-решения.

Требования:

1. No-op является реализацией по умолчанию для разработки, тестов, отсутствующей конфигурации и отказа пользователя.
2. Каталог событий представляет собой типизированную карту `event -> allowed payload`.
3. Нельзя передавать произвольный `Record<string, unknown>` из компонентов.
4. Sanitizer рекурсивно очищает вложенные данные до сериализации и использует default-deny.
5. Общий модуль управляет жизненным циклом всех адаптеров и не допускает повторной инициализации.
6. Компоненты не обращаются к `ym`, `gtag`, `dataLayer` и другим глобальным API напрямую.

## Этап 2. Consent management

Связанный issue: #8.

Ввести состояния:

- `unknown`;
- `granted`;
- `denied`.

Хранить решение, версию политики, время выбора и источник изменения. Для гостя локальное решение является источником истины на устройстве. Для авторизованного пользователя оно дополнительно синхронизируется с backend, не блокируя применение локального отказа.

Требования:

1. До выбора и при отказе внешние SDK и сетевые запросы не создаются.
2. Согласие не отмечено заранее; действия согласия и отказа визуально равнозначны.
3. Отказ не влияет на основные функции сайта.
4. Решение изменяется в настройках приватности без обязательной перезагрузки.
5. При отзыве адаптеры прекращают отправку, сбрасывают состояние и удаляют известные analytics cookies/local keys.
6. Существенное изменение целей, провайдеров или набора данных повышает consent policy version и переводит решение в `unknown`.
7. Строго необходимое локальное хранение авторизации и настроек явно отделено от необязательной аналитики.

## Этап 3. Безопасное отслеживание Vue Router

Связанный issue: #11.

1. Отправлять page view только после успешного завершения навигации.
2. Использовать route name или безопасный route template вместо `fullPath`.
3. Не отправлять query string, fragment и реальные route params без явного allowlist.
4. Учитывать redirects, navigation failure и отменённую навигацию.
5. Нормализовать или полностью исключить OAuth callback, email confirmation, password reset, chat invite, shared playlist/excerpt tokens, поиск, приватные чаты и admin routes.
6. Один завершённый переход создаёт не более одного page view независимо от повторного render/hydration.

## Этап 4. Адаптеры провайдеров

Связанные issues: #6, #7.

Сначала реализовать Яндекс Метрику. Google Analytics оставить отдельным опциональным адаптером и не включать без подтверждённой необходимости.

Требования:

1. Скрипт загружается динамически только после `granted` и при валидной environment-конфигурации.
2. Идентификаторы счётчиков не хранятся в коде или тестовых fixtures.
3. Пустая или некорректная конфигурация безопасно выбирает no-op.
4. Инициализация идемпотентна; SPA page view не дублируются.
5. Webvisor, session replay, рекламная персонализация и User-ID выключены.
6. Provider errors изолированы и не ломают приложение.
7. CSP разрешает только точные необходимые provider hosts.
8. Отзыв согласия вызывает provider consent update/reset и прекращает дальнейшие запросы.

## Этап 5. Минимальные продуктовые события

Связанный issue: #12.

Начальный каталог:

- применение группы фильтров без текста поиска и выбранных значений;
- открытие карточки с безопасным `source`;
- фактический запуск воспроизведения;
- выбор сезона или серии без названия и ID аниме;
- подтверждённое изменение статуса библиотеки;
- успешное создание плейлиста с типом видимости;
- успешная публикация с безопасной категорией вложения;
- техническая ошибка как стабильный код.

Каждое событие должно отвечать на конкретный продуктовый вопрос. События успеха отправляются только после подтверждённого результата API или фактического начала операции, а не при клике или render.

## Этап 6. Обезличенная error/performance telemetry

Связанный issue: #13.

Разрешённые данные:

- стабильный error code;
- route template;
- release/build version;
- технические тайминги и Web Vitals;
- online/offline;
- крупная категория устройства или браузера без fingerprinting.

Запрещённые данные:

- DOM-текст;
- request/response body;
- Authorization и Cookie headers;
- query string и fragment;
- пользовательский контент;
- названия файлов;
- console breadcrumbs;
- session replay;
- неочищенный stack trace с приватными URL.

До подключения telemetry заменить прямое логирование error objects на безопасный внутренний logger с кодами и sanitizer.

## Этап 7. Экспорт, удаление и сроки хранения

### Экспорт

1. Использовать реальный `DataExport` со статусами `queued`, `processing`, `ready`, `expired`, `failed`.
2. Создавать архив фоновой Celery-задачей и валидировать выбранные категории.
3. Выгружать только данные субъекта. Не включать чужие email, телефоны и содержимое сообщений, на которое пользователь не имеет права экспорта.
4. Добавить авторизованные list/status/download endpoints.
5. Скачать архив может только владелец; ответ имеет `private, no-store`.
6. Архив удаляется по TTL вместе с физическим файлом.
7. UI показывает фактические статус, размер и срок удаления, без фиктивных оценок и обещаний email.

### Удаление аккаунта

1. Оставить один согласованный контракт: честное немедленное удаление либо реальный schedule/cancel lifecycle.
2. Проверять пароль и, когда включена 2FA, второй фактор.
3. Отзывать refresh/access sessions, web push subscriptions и связанные credentials.
4. Удалять физические файлы, экспорты, локальные provider identifiers и данные аналитики.
5. Выполнять операции транзакционно или через идемпотентный cleanup workflow с повтором.
6. Сохранять только минимальный audit record, если он юридически необходим, без пользовательского содержимого.
7. Добавить доказательные тесты БД, файлового хранилища и повторного выполнения cleanup.

### Retention matrix

Документировать для каждой категории цель, основание, источник, получателей, срок хранения, способ удаления и экспортируемость. Минимальные категории: аккаунт, сессии, security logs, сообщения, публикации, файлы, watch history, рекомендации, product analytics, error telemetry, exports и provider cookies.

## Этап 8. Тесты, CI и документация

Связанный issue: #14.

### Frontend unit tests

- state machine consent и version upgrade;
- отсутствие provider load для `unknown/denied`;
- idempotent initialization;
- sanitizer для вложенных объектов и запрещённых ключей/значений;
- отклонение неизвестного события и поля;
- route normalization и token/query non-leakage;
- provider mocks и reset после отзыва;
- отсутствие дублей при повторном render.

### Backend tests

- privacy settings read/update и user isolation;
- корректность consent sync;
- export ownership и отсутствие чужих данных;
- download authorization и TTL cleanup;
- account deletion, token revocation и physical file cleanup;
- идемпотентность cleanup;
- запрет приватного содержимого в логах и telemetry payload.

### Browser/integration tests

- ни одного analytics-запроса до согласия;
- отсутствие запросов после отказа и отзыва;
- ровно один page view после успешной SPA navigation;
- sensitive routes не раскрывают token/query/params;
- consent UI доступен с клавиатуры и на mobile;
- отказ не меняет функциональность и внешний вид приложения за пределами consent UI.

### Архитектурные проверки

- запрет `ym`, `gtag`, `dataLayer` и прямых analytics scripts вне `src/analytics/adapters/`;
- запрет произвольных payload из компонентов;
- перечень внешних endpoints в документации;
- реальные provider IDs отсутствуют в fixtures и репозитории;
- новые провайдеры не обходят consent, catalog и sanitizer.

## Последовательность реализации

1. P0 privacy settings, `UserAnalytics`, export и deletion defects.
2. Issues #5, #9, #10: core, sanitizer, catalog.
3. Issue #8: consent state, backend sync и UI.
4. Issue #11: безопасная SPA navigation analytics.
5. Issue #6: Яндекс Метрика.
6. Issue #7: Google Analytics только при подтверждённой необходимости.
7. Issues #12 и #13: минимальные events и telemetry.
8. Реальный data export, deletion lifecycle и retention matrix.
9. Issue #14: полный audit, CI enforcement и эксплуатационная документация.

Каждый этап должен завершаться тестами и может быть отдельным логическим коммитом или pull request. Нельзя подключать production provider до завершения этапов 0-3.

## Definition of Done

- При `unknown` и `denied` отсутствуют внешние analytics-запросы и provider cookies.
- Consent можно дать, отклонить, изменить и отозвать.
- Один успешный SPA-переход создаёт не более одного page view.
- Sensitive routes никогда не раскрывают token, query, fragment и raw params.
- Все events определены в типизированном каталоге и проходят sanitizer до сериализации.
- Пользовательский контент и персональные данные отсутствуют в analytics, telemetry, traces и тестовых артефактах.
- Экспорт действительно создаётся, доступен только владельцу и не содержит чужих данных.
- Удаление аккаунта очищает БД, файлы, сессии, токены, push и analytics state.
- Политика приватности содержит оператора, провайдеров, цели, категории данных, трансграничные передачи и сроки хранения.
- Frontend, backend, Playwright, visual и CI-проверки проходят без подавления ошибок.

## Внешние данные, необходимые до production-включения

- подтверждённые ФИО/наименование и адрес оператора персональных данных;
- фактическое место размещения основной инфраструктуры и применимые правила локализации;
- утверждённые цели, основания и сроки хранения;
- решение о необходимости Google Analytics;
- production identifier Яндекс Метрики и, при необходимости, GA measurement ID через secrets/environment;
- подтверждение списка внешних получателей и трансграничных передач.

Разработку core, sanitizer, catalog, consent и тестов можно начинать без production identifiers.
